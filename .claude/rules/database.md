# Database (self-hosted PostgreSQL / Drizzle)

- **Never modify an existing migration.** Always create a new one via `npx drizzle-kit generate`. Existing migrations may have already run in production.
- RLS must be enabled on every table. Never skip it. Since there's no Supabase Auth session to read, RLS policies (`drizzle/rls-policies.sql`) use `current_setting('app.user_id', true)::uuid` / `current_setting('app.user_role', true)` — these must be `SET LOCAL` per request-scoped transaction by the app layer (`lib/db/index.ts`), not assumed to exist automatically.
- Schema lives in `drizzle/schema.ts` — it is the source of truth for types across `lib/validations/`, actions, and components (no more `types/database.ts` generation step).
- The `tenants_public` view (`drizzle/tenants-public-view.sql`) and admin RPC functions (`drizzle/rpc-functions.sql`) are hand-ported SQL, not generated by drizzle-kit — apply them alongside the generated migration file, and update them by hand if the underlying tables change.
- Never seed production data in migration files. Use dedicated seed/data-migration scripts (see `drizzle/migrate-data.ts` for the pattern).
- Never drop columns or tables without confirming data is no longer needed.
- Add indexes in their own migration, not bundled with schema changes.
- DB client: `lib/db/index.ts` (Drizzle + `node-postgres`) — a module-level singleton, not per-request like the old Supabase client factories. Query via `db.select()...from(table)` against `drizzle/schema.ts`'s exported tables.
- FK constraints from `users` → `tenants.userId`/`revenueReports.userId`/`moderanSyncLog.sentBy` are enforced (added in `drizzle/migrations/0002_black_umar.sql`).
